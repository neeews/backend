## 환경과 가정

- 측정 PC: Core Ultra 7 155H(16코어/22스레드), RAM 15.6GB(측정 중 가용 약 0.1~2GB), Windows 11. 앱·MySQL·k6를 같은 PC에서 돌렸다.
- 앱: JDK 21, `-Xms512m -Xmx1g`, 스케줄러 끔. MySQL 8.0.43 임시 인스턴스(기본 설정: 버퍼 풀 128MB, binlog 켬). 운영은 8.4 컨테이너지만 기본 설정이 같다.
- 데이터: **합성 데이터** 기사 10만 건(45일, 평균 본문 893자, 테이블 272MB), 오늘 기사 1,607건, 오늘 요약 후보 85건, 테스트 계정 200개. 분포는 코드 주석·커밋 메시지의 수치(본문 평균 1,018자/359자, 요약 컷 0.93)에 맞췄고 `seed.py`에서 바꿀 수 있다. 9월 초 운영 기사 ID가 이미 8만 번대였다(`labels/importance_seed.sql`).
- 부하 모델: 도착률 고정(constant-arrival-rate), 워밍업 10초 + 측정 40초. 첫 조회 크롤링은 가짜 언론사(응답 1초)로 흉내 냈다.
- 측정 중 가용 메모리가 바닥까지 내려간 구간이 있었다(샘플 최소 1MB, 페이지 입력 최대 약 1,000/초). 페이징의 영향을 완전히 배제하지는 못했다. 같은 조건에서 전후를 나란히 쟀고 손대지 않은 API(대조군)가 안정적이었던 점이 근거다.
- **절대 수치는 운영과 다르다.** 이 PC는 운영 VPS보다 빠를 가능성이 크고, Windows MySQL은 파일 캐시를 쓰지 않아 랜덤 읽기가 느리다. 전후 **비율과 병목의 모양**을 보는 용도다. 사용 CPU가 약 1.5코어였던 검색 1건은 코어가 적은 서버에서 더 일찍 포화한다.

## 1. 검색 (`/search`)

**원인.** `LOWER(title) LIKE '%q%' OR LOWER(description) LIKE '%q%'`는 인덱스를 못 타서 요청마다 테이블 전체(272MB)를 훑고, 총개수용 COUNT가 같은 스캔을 한 번 더 한다. 검색 1건이 DB 코어 약 1.5개를 쓰고, 풀(10개)이 동시에 10건으로 차면 나머지는 커넥션을 기다리다 30초 후 실패한다. 6 RPS에서 실제로 앱 로그에 `HikariPool-1 - Connection is not available, request timed out after 30011ms (total=10, active=10, idle=0, waiting=109)`가 212줄 남았다.

**개선.** MySQL ngram FULLTEXT 인덱스(`migrations/20261001_article_fulltext_ngram.sql`)로 검색한다. 매칭이 3,000건을 넘는 흔한 검색어는 FULLTEXT 결과를 전부 정렬하는 비용이 커서(2만 건에 약 3초) 최신순 인덱스를 따라가는 경로로 처리한다. 2글자 미만 검색어는 기존 LIKE를 쓴다.

| 부하 | 구분 | 개선 전 p95 | 개선 후 p95 |
|---|---|---|---|
| 1 RPS | 전체 (중앙값) | 3.9초 (3.6초) | 1.4초 (49ms) |
| 3 RPS | 전체 (중앙값) | 20.2초 (13.8초) | 1.0초 (28ms) |
| 6 RPS | 전체 (중앙값) | 35.5초 (30.0초), 실패 33.5% | 1.4초 (25ms), 실패 0% |
| 20 RPS | 전체 (중앙값) | (6 RPS에서 이미 붕괴) | 1.8초 (26ms), 실패 0% |
| 3 RPS | 중간 단어(환율·삼성전자) | 20.5초 | 57ms |
| 3 RPS | 희소 단어(손흥민·태풍) | 20.0초 | 35ms |
| 3 RPS | 결과 없음 | 13.3초 | 12ms |
| 3 RPS | 흔한 단어(정부·대통령·연합뉴스·기자) | 20.2초 | 1.5초 |

- 개선 후 20 RPS에서 MySQL CPU 평균 2.9코어(개선 전 3 RPS에서 평균 8코어).
- 전체 p95가 1초대로 남는 이유는 흔한 단어(요청의 20%)다. 아래 "한계" 참고.
- FULLTEXT 인덱스 비용: 구축 156.7초(10만 건, 이 동안 쓰기 차단), 디스크 약 213MB 추가(FULLTEXT 보조 파일 169MB, `articles.ibd` 292 → 336MB).

## 2. 메인 화면 (`/articles/hot|latest|breaking|headlines|today`)

**원인.** 비로그인이면 누가 불러도 같은 결과인데 요청마다 DB 조회와 계산을 반복한다. 특히 `/articles/today`는 후보 기사 쌍마다 비그램 집합을 새로 만들어 O(N²)로 비교하고(요청당 중앙값 741ms, 초당 1회당 자바 CPU 약 1코어), 그동안 **DB 커넥션을 쥔다.** 그래서 초당 10명이 메인 화면을 열면 풀(10개)이 마르고, 계산이 없는 `/latest`·`/hot`·`/breaking`·`/visits/ping`까지 중앙값 3.6초가 된다.

**개선.** Caffeine 캐시(속보·최신·핫이슈·헤드라인 60초, 오늘의 뉴스 5분)를 두고, 만료 순간에 몰린 요청은 한 번의 계산을 같이 기다린다. 읽음 표시는 캐시된 목록 위에 쿼리 한 번으로 덧씌운다 (로그인 `/headlines`: 카테고리마다 반복하던 쿼리가 1회로).

| 메인 화면 로딩 (초당) | 개선 전 p95 | 개선 후 p95 | 개선 전 자바 CPU | 개선 후 자바 CPU |
|---|---|---|---|---|
| 5회 | 805ms | 7ms | 평균 5.2코어 | 0.2코어 |
| 10회 | 8,910ms | 5ms | 9.8코어 | 0.2코어 |
| 20회 | 33,548ms | 4ms | 10.2코어 (포화) | 0.3코어 |
| 30회 | 44,650ms | 4ms | 10.2코어 (포화) | 0.2코어 |
| 100회 | - | 4ms | - | 0.7코어 |
| 300회 (초당 약 1,800 요청) | - | 4ms (p99 242ms, 실패 0) | - | 2.0코어 |

- `/articles/today` 요청당 중앙값 741ms → 2ms. 계산은 5분에 한 번(첫 요청 약 0.6초)만 한다.
- 대신 속보·최신 등 반영이 최대 60초, 오늘의 뉴스가 최대 5분 늦다.

## 3. 기사 상세 (`/articles/{id}`)

**원인 (두 가지).**
1. `@Transactional` 안에서 외부 사이트 크롤링(최대 10~15초)을 `join()`으로 기다려 DB 커넥션을 계속 쥔다. 첫 조회가 몰리면 풀이 말라 다른 API가 멈춘다. 같은 기사를 동시에 열어도 크롤링이 요청 수만큼 반복된다.
2. 엔티티로 `viewCount++` 하여 동시 조회가 서로의 증가분을 덮어쓴다.

**개선.** 트랜잭션을 [조회 → (밖에서) 크롤링 → 저장]으로 나누고, 크롤링은 전용 스레드풀(64)에서 같은 기사에 한 번만 실행한다. 조회수는 `UPDATE ... SET view_count = view_count + 1`로 올린다.

| 시나리오 | 개선 전 | 개선 후 |
|---|---|---|
| 캐시 히트 100 RPS | p95 9ms | p95 9ms (변화 없음) |
| 캐시 히트 300 RPS | p95 5ms | p95 7ms (변화 없음) |
| 한 기사에 50 동시 (30초) | 23,657건 중 **90.0% 유실**, p95 92ms | 26,722건 **유실 0%**, p95 101ms |
| 신규 기사 40건 동시 첫 조회 ×2회 (가짜 사이트 1초) | 다른 API p95 2.9~3.3초(최대 4.0초), 폭주 요청 p95 4.5초 | 다른 API p95 13ms(최대 65ms), 폭주 요청 p95 2.2초 |
| 가짜 사이트 최대 동시 요청 | 20 (커넥션 10개 × 2) | 64 (스레드풀 상한) |

- 핫 기사 p95가 소폭(92 → 101ms) 늘었다. 이제 모든 증가가 실제로 반영되며 같은 행의 UPDATE가 직렬화되기 때문이다.

## 대조군

손대지 않은 카테고리 목록(6 RPS)이 전후로 같게 나왔다. 최신순 p95 15ms → 15ms, 심층 페이지 17 → 19ms. 환경 변동은 이 정도다. (인기순은 p95 2.7초 → 2.1초로 보이지만 측정 환경 차이로 보고 개선으로 세지 않는다.)

## 한계와 남은 과제

- **흔한 3글자 이상 구문의 총개수.** FULLTEXT 엔진이 `대통령`·`연합뉴스` 같은 구문의 개수를 세는 데 단독 실행 기준 2.5~3.3초가 든다(기존 LIKE 총개수는 1.2~1.8초, 본문 조회까지 합치면 3.7초였다). 총개수 캐시나 상한 표기가 필요하다.
- **정렬 의미 변경.** 매칭 3,000건 초과 검색어는 제목 일치 우선 정렬 없이 최신순이다. 1글자 검색어와 기호만 있는 검색어는 기존 LIKE 경로라 여전히 수 초 걸린다.
- **카테고리 인기순 목록은 그대로 느리다.** 요청당 약 2초(중앙값 1.7~2.1초). 7일치 행 전체에 계산식 정렬을 건다.
- **`articles.link` 유니크 인덱스가 만들어지지 않는다 (운영 확인 필요).** `link varchar(1000)`이 utf8mb4에서 4,000바이트라 인덱스 생성이 `ERROR 1071`로 실패하고 Hibernate는 이를 조용히 넘긴다. 이 환경에서는 인덱스가 없었다. 운영도 같다면 RSS 수집의 `existsByLink`가 기사마다 테이블을 훑는다 (10만 건에서 없는 링크 약 650ms, 있는 링크 약 300ms, 프리픽스 인덱스 `link(255)`를 만들면 1ms 안팎). 운영에서 `SHOW INDEX FROM articles;`로 확인할 것.
- **헬스체크가 SMTP를 호출한다.** `/actuator/health`가 메일 헬스 인디케이터로 호출마다 SMTP에 로그인한다. `management.health.mail.enabled=false`를 권장한다.
- 합성 데이터와 단일 PC 측정이라 운영 수치와 다르다. 운영 VPS 사양에 맞춰 CPU를 제한하거나 스테이징에서 같은 스크립트로 다시 재는 것이 좋다.
